# Аудит библиотек AgiSpace: Тонкие сигналы и здоровье репозиториев

Дата проверки: 21 сентября 2026. Подготовлено для Павла Шаца.

## 1. Главный вывод

У нас уже есть сильная библиотека предметной методологии и управления агентной разработкой. Наиболее полезное сочетание для «Тонких сигналов»: **план v6.1 + AgiSpace Opportunity Radar 0.1.1 + выбранные модули Product Opportunity Lab + существующий backend**. Для поддержания качества собственного кода: **Desloppify + один GOAL-контроллер + CI и независимая проверка**. Для хакатонного **SourceCraft Repo Health** отдельно нужны интеграция с SourceCraft, фактические AppSec-данные и собственный объяснимый скоринг.

Это три связанных, но разных результата. Ни один найденный пакет сам по себе не закрывает все три.

**Основной недостаток библиотеки — разрыв между методологией и исполняемыми гарантиями.** Инструкция требует доказательств, но отдельные helpers пропускают пустые доказательства; manifest объявляет роль, но не запускает её; сохранённый отчёт о работе сервиса не подтверждает его здоровье сегодня.

### Обязательные условия «Тонких сигналов», влияющие на рейтинг

Исходный PDF требует открытый запрос и живой поиск, ТОП-15, исключение зрелых технологий и хайпа, преимущества и кейс-примеры, проверяемые источники, русскоязычный интерфейс и объяснения. Нужны даты, тип, язык и доверенность источников; для генеративного перевода/резюме — маркировка. PostgreSQL и Docker указаны в программных требованиях.

Есть отдельное требование **обучения модели** и ориентир 75–80% качества. План v6.1 честно фиксирует конфликт с вариантом полностью без обучения. Prompt engineering нельзя выдавать за обучение. Практическая адаптация: frozen embeddings/LLM + небольшой обучаемый классификатор по признакам, если это соответствует согласованной методике; отдельная оценка на новых размеченных примерах. Все 100 исходных строк уже использованы при проектировании паттернов, поэтому они не являются нетронутым holdout.

ТЗ ограничивает облачные модели и требует согласования других моделей/внешних маршрутизаторов. В продукте нужен явный allowlist и журнал выбора; настройки операторских агентов backend не следует копировать в продукт автоматически.

### Обязательные условия Repo Health

Шесть исходных категорий: документация и лучшие практики, CI/CD, Security, активность, issues, состояние кода/технический долг. ТЗ допускает обоснованное объединение или исключение категории с объяснением влияния на score. Отсутствие данных должно отображаться отдельно от плохого результата.

**Security опирается на фактические AppSec SourceCraft**: доступные SAST/SCA/secret scanning и статусы исправления. Desloppify, собственный Semgrep или OpenSSF Scorecard не заменяют этот пункт. Я ID подтверждает вход пользователя, а доступ к репозиторию требует отдельной проверки полномочий. Это согласуется с [моделью доступа SourceCraft](https://sourcecraft.dev/portal/docs/ru/sourcecraft/security/).

## 4. Как читать рейтинг

Баллы — экспертная оценка применимости, **не benchmark, вероятность успеха или процент готовности**. S = Тонкие сигналы; H = продукт SourceCraft Repo Health; A = автоматизация собственной разработки.

- **5:** прямо закрывает центральную потребность или задаёт обязательный предметный контракт.
- **4:** существенно полезен, нужна ограниченная предметная интеграция.
- **3:** вспомогателен либо требует заметной переработки.
- **2:** узкий эксперимент/поздняя очередь.
- **1:** слабая связь с текущим результатом.

Готовность указывается отдельно: **код** — есть исполняемые компоненты; **skill** — инструкции и ограниченные helpers; **план** — проект решения; **запись эксплуатации** — сведения Git-ledger, без сегодняшнего smoke-test. Приоритет P0 означает включить в ближайшую работу, P1 — после обязательного пути, P2 — лаборатория/позже. Высокая полезность плана не означает готовый продукт.

### Приоритеты по задачам

**S — Тонкие сигналы:** L01 → L02 → L03 → инфраструктурные возможности L06 → L08/L09 → отдельные контракты L04/L05 → L14/L16 → OpenResearch только для R&D.

**A — автоматизация разработки:** существующий L04 → CI и критерии → Desloppify → L07/L09/L10 → выбранные шаблоны L05/L11 → L17. Для целого жизненного цикла добавить release/observability-проверки, а не только оценку чистоты кода.

## 7. Результаты проверок: конкретные слабые места

### F01. POL принимает пустые доказательства — воспроизведено сейчас

`audit_evidence.py` был вызван с пустым JSONL и штатным `overclaim_candidates.json`. Результат: код завершения **0**, `Records: 0 | Structural errors: 0`. При этом штатный `tests/test_scripts.py` завершился успешно.

Последствие: «проверка завершилась успешно» нельзя превращать в разрешение публикации сигнала или выпуска кода. Исправление: обязательные critical claims, evidence coverage на каждый claim, происхождение и достаточность для решения, отдельные schema/semantic verdicts. Остальные известные дефекты POL — maturity прогнозов, slug traversal, восстановление installer, mixed profiles — подтверждены текущим операционным документом Git, но заново все не воспроизводились.

### F02. Radar допускает структурно корректное production-решение с пустым ledger — воспроизведено сейчас

Вызван `validate()` из 0.1.1: sources/claims пусты, gate PASS без evidence, решение PRODUCTION BUILD/R4. Результат: **errors=[]**, только предупреждение `empty claim ledger; this is only a template`.

Сам validator прямо объявляет себя структурным и требует semantic review. Дефект интеграции возникает, если потребитель трактует этот PASS как предметное разрешение. Нужен отдельный строгий профиль для публикации/действий; шаблон можно сохранить валидным как шаблон. Дополнительно проверять существование узлов графа и evidence у положительных gates.

### F03. Reference policy v6.1 не полностью валидирует типы — воспроизведено сейчас

15 штатных тестов прошли. Пробы `novelty=[]` и `critical_claims=[{}]` вызывают `TypeError` при проверке принадлежности множеству. Проба `evidence_events=3, independent_origins=100` получает RANK_ELIGIBLE: перекрёстные ограничения счётчиков не заданы.

Последний результат — неоднозначность контракта, а не автоматически доказанная ложная классификация: несколько независимых организаций могут исследовать одно событие. Нужно определить, что считается origin/event, и получать агрегаты из реальных связей ledger, а не принимать произвольные числа. Типы проверять до membership; API должен возвращать контролируемую ошибку или HOLD. Reference policy — пример логики, не полный evidence engine.

### F04. Auto-Goal: процессное VERIFIED не равно доказанному результату

В архивном аудите 17.09 зафиксированы: legacy-путь без строгих требований, слабый контракт increment, неидемпотентный checkpoint, пустой стандартный verifier context после COMPLETED, принятие текстовой evidence-заявки, несвязанность manifest digest с payload, необозначенное усечение evidence, повторное положительное решение без явного закрытия прежнего blocker.

Это выводы о **0.3.0-portable.1 / commit 4e3257d8…**, а не утверждение, что каждый дефект остался в текущем main. В этой работе текущий kernel не был полностью сравнен и протестирован. Нужны проверка исправлений по каждому AGxx и повторный conformance-run до продуктового использования. Текущий skill содержит полезные ограничения, но текст инструкции не доказывает их enforcement.

### F05. Конфликт обязательного обучения и harness-first

Сохранённый план уже признаёт конфликт с буквальным ТЗ. Необходимо реализовать обучаемый компонент и обоснованную оценку либо получить подтверждение допустимости иной трактовки. 100 позитивно отобранных карточек недостаточно для честной демонстрации отделения шума и зрелых технологий. Нужны отрицательные/пограничные примеры, group/time split и отдельный evaluation set.

### F06. Устаревающие источники истины

В старом Source Register каноном назван v4; актуальный отдельный документ и пакет — v6.1. Research Kit содержит историю, поэтому его агрегатор не может автоматически назначать последнюю норму. В текущем CONTINUATION_POINT есть свежий STT-абзац GigaAM и сохранённая более старая формулировка о Parakeet/Whisper. Это наглядный риск накопительного ledger: выбирать датированное решение с evidence, а не первое совпадение слова canon.

Решение: реестр `component_id → canonical_version → source_hash → supersedes → verified_at → environment`. Отдельные даты создания, обновления документа и проверки runtime.

### F07. Разные контроллеры решают одну задачу

GOAL, GoalOps, Cursor curator, stop-hook, HoH-петля и OpenResearch потенциально конкурируют за следующий шаг. Текущий AGENTS.md уже требует один GOAL-контроллер. Остальные подключать как фазы, адаптеры или изолированную лабораторию. Scheduler доставки задач и контроллер предметного решения имеют разные роли.

### F08. У backend-профиля и продукта разные границы доступа

Эксплуатационные записи описывают широкие операторские права. Worker, читающий чужой репозиторий или страницу, должен иметь отдельные ограничения. README/AGENTS/issues анализируемого проекта — данные, а не источник полномочий. Это непосредственно относится к обеим задачам: внешнее содержимое поступает в LLM.

### F09. Лицензии и авторство заполнены неравномерно

Radar manifest явно называет Pavel Shats; POL LICENSE — contributors; Auto-Goal export указывает отсутствие отдельной лицензии источника. Владение GitHub-репозиторием не устанавливает авторство всего кода. Для распространения пакетов нужен раздельный реестр own code / third-party / generated / reconstructed с лицензиями и pins. Неизвестное авторство в каталоге оставлено неизвестным.

## 8. Практическая адаптация

### Тонкие сигналы: что переносить первым

1. Заморозить v6.1 как нормативную основу; Radar 0.1.1 и POL 1.2.1 — доноры. Сохранить 18 механизмов и шесть предикторов, но считать их гипотезами правил, проверяемыми на данных.
2. Реализовать PostgreSQL-сущности `source`, `document_snapshot`, `claim`, `event`, `origin`, `signal_candidate`, `run`, `evaluation`; хранить as_of, даты доступности, model/prompt/schema versions, hash и provenance.
3. Перенести из Radar evidence/counterevidence, из POL — адаптивное углубление и остановки. Решения RANK/WATCH/HOLD/REJECT выполняет типизированный domain-код. Бизнес-readiness R4 не является ранностью сигнала.
4. Сделать реальный открытый поиск и extraction. Поиск, извлечение, проверка, ранжирование и UI имеют отдельные контракты. Ссылку из поисковой выдачи не считать прочитанным источником.
5. BGE-M3 — поиск/дедуп, BERTopic — вспомогательная группировка. Отдельный путь сохраняет одиночный ранний сигнал, который ещё не образовал кластер. [BERTopic topics-over-time](https://maartengr.github.io/BERTopic/getting_started/topicsovertime/topicsovertime.html) не заменяет detector роста и требует осторожности с будущими данными.
6. Довести вопрос обучения и evaluation; выдавать отдельно score ранности, полноту evidence и калиброванную уверенность, если она действительно измерена.
7. Закрыть пользовательскую приёмку: русский запрос → поиск → до 15 подходящих результатов с доказательствами. При нехватке качественных кандидатов показать нехватку и продолжение поиска, а не дополнять список зрелыми технологиями ради числа.

Оценка адаптации узких донорских частей для одного инженера: строгие схемы/validator-профили **1–3 дня**, перенос предметных веток **2–4 дня**, bounded RuntimeAdapter **2–4 дня**. Это плановые диапазоны, не измеренные сроки; полноценный продукт, доступы, обучение и сбор evaluation-набора в них не входят.

### SourceCraft Repo Health: что действительно сокращает разработку

1. Сначала проверить реальные API/CLI и способ получения AppSec для доступного репозитория. Сохранить ответ с датой, областью прав и версией сканирования; отсутствие данных показывать явно.
2. Считать метрики воспроизводимым кодом. Для каждой хранить source, commit, measured_at, analyzer_version, status и reason. Общая оценка и coverage — отдельные поля; при частичной доступности не делать вид, что проекты полностью сопоставимы.
3. Начать Code Health с простого baseline scc/Git/PyDriller. Для Desloppify сделать сменяемый provider; его внутренний score не подставлять как весь Repo Health Score.
4. Добавить Я ID, проверку доступа к собственному репозиторию, периодический пересчёт, рейтинг, детализацию и Markdown-экспорт. LLM-summary необязателен для расчёта и не изменяет цифры.
5. Repowise допускать по пилоту: небольшой/крупный репозиторий, две языковые группы, повторный запуск на том же commit, качество findings, время/память. Graphify оставить для текущей разработки до такого сравнения.

Оценка: proof-of-access/API/AppSec **0,5–2 дня**, типизированный collector и базовый score **2–5 дней**, Desloppify adapter **1–2 дня** после подтверждения CLI-схемы. Если нужные AppSec-данные не выдаются, календарный срок зависит от организаторов; программный обход этого требования не предполагается.

### Автоматизация чистоты собственного репозитория

Рекомендуемый цикл: изменение → детерминированные проверки CI → Desloppify scan → приоритизированное исправление в отдельной ветке → тесты и review → повторная оценка → решение о слиянии. GOAL владеет целью и завершением; Desloppify — находками; CI — результатами проверок.

В upstream Desloppify предусмотрены CI-профиль и JSON status; CI-профиль пропускает медленные/субъективные стадии. Полные и механические результаты сравнивать раздельно. Сканировать связный проект целиком, отдельно для frontend/backend; не обещать diff-only ускорение. Внедрение этой схемы здесь спроектировано, но на сервере не выполнено. [Основание](https://github.com/peteromallet/desloppify).

Начальная приёмка: зафиксированный baseline; новая воспроизводимая проблема вызывает failing gate; исправление подтверждается повторным запуском; сломанные тесты блокируют положительный вывод даже при росте health-score; остановка/retry сохраняют состояние. Цель «score 100 любой ценой» непригодна: предпочтительнее отсутствие новых серьёзных проблем и доказанное исправление приоритетного долга.

Для полного Change Lifecycle Agent добавить связь `change_id → commit → CI → release → telemetry → regression`. Без этой связи чистота репозитория ничего не доказывает о корректности выпуска и влиянии на пользователей.

## 9. Что отложить

- ThoughtState / Symbiont / «мыслеобразы»: самостоятельный R&D, не доказанное сокращение пути к двум кейсам.
- Bifrost migration: выполнять по отдельному основанию, не вместе с продуктовым MVP.
- Одновременное подключение всех harnesses, новых memory engines и графовых систем: слишком много владельцев состояния.
- Старые Evolution/WavePack и ремонтные архивы: история и точечные доноры, не пакетная установка.
- Media Factory, брендовые, CAD, медицинские, карьерные и Android/Kali материалы: не относятся к центральным функциям этих двух кейсов. Они оставлены в полном inventory без фиктивных оценок пригодности.

## 10. Как привести библиотеку в порядок

Ввести одну карточку на компонент, а не на каждый ZIP: ID, назначение, автор/основание атрибуции, first_seen, release_date, saved_at, upstream, license, pin/hash, canonical artifact, supersedes, зависимости, интерфейсы, evidence, known defects, runtime status, last_verified_at, владелец сопровождения.

Развести типы: **runtime / skill / executable helper / dataset / implementation plan / audit / archive / reconstruction**. Затем состояния: proposed → reviewed → integrated → runtime-verified → deprecated. Переход в runtime-verified требует датированного smoke/acceptance, а не наличия README или прошлой фразы «установлено».

Предлагаемая консолидация: один актуальный каталог Radar, один POL, один GOAL; архивные версии сохраняются для provenance. Для каждого проекта — короткий lock-файл с выбранными версиями и критериями, без загрузки всей исторической библиотеки в prompt.
