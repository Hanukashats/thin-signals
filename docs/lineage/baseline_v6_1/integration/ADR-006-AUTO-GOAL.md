# ADR-006: перенос механизмов Auto‑Goal в Thin Signals

Дата: 2026-09-17. Статус: архитектурное решение этого плана; реализация pending.

## Контекст

План v6 уже использует PG/Procrastinate, Hermes adapter, evidence ledger и 18 предметных паттернов. Auto‑Goal добавляет полезную дисциплину целей, но его файловый kernel не должен конкурировать с этим состоянием. Проверены commit 4e3257d8c6f4ddf05f88920db6e9509b79bd1c58, 59 штатных тестов и 14 дополнительных проб.

## Решение

1. Встроить `goal_control` как модуль существующего Python backend, с формальными схемами и транзакционными командами.
2. Адаптировать compiler/catalog/context concepts; сохранять происхождение заимствованного кода и применимые права. Не копировать весь kernel/installer/hook как новую production-платформу.
3. PG — единственный writable ledger; Procrastinate доставляет jobs, Hermes выполняет разрешённые задания. LangGraph остаётся резервом; OpenCode проверяется тем же adapter acceptance.
4. Разделить process completion, verification, claim state и signal decision. Проверенное исследование может дать REJECT/HOLD.
5. Верифицировать frozen candidate с полным индексом evidence и unresolved findings; не полагаться на текстовый PASS.
6. Критерии immutable в ревизии; эволюция создаёт новый snapshot с явным impact и переносом только валидных результатов.
7. Локальный Auto‑Goal для разработки — отдельный добровольно подключаемый контур после исправлений; он не управляет runtime пользователей.

## Рассмотренные варианты

- Взять весь daemon: быстро для одиночного локального процесса, но появляется второй ledger и необходимость решать auth/idempotency/recovery дважды. Отклонено для product runtime.
- Взять только SKILL.md: удобно стартовать, но существенные ограничения остаются обещаниями в тексте. Недостаточно для продуктовых gates.
- Переписать весь стек на новый оркестратор: не связано с обнаруженными проблемами и увеличивает риск срока. Отклонено.
- Перенести механизм в существующий domain: выбран; минимизирует новые сервисы, сохраняет полезную компиляцию и проверяемость.

## Последствия

Нужны IterationContract, revision/idempotency/receipts, principal policy, typed research progress и verification bundle. Всё это развивается в уже запланированных схемах и backend. Нельзя считать присвоенный run VERIFIED доказательством качества технологии или ценности инвестиции.

## Условия пересмотра

Решение пересматривается отдельным ADR, если измерены ограничения текущей очереди/контекста, либо upstream предоставляет нужные durable/auth/contract guarantees и миграционный выигрыш подтверждён. Число скиллов или название framework не являются достаточным основанием.

## Приёмка

`acceptance.json`; все изменения имеют requirement IDs и receipts. Статус этого ADR не означает, что эти проверки уже прошли на backend.
