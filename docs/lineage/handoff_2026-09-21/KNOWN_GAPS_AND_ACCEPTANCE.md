# Известные недоработки и приёмка адаптации

1. **policy.py:** 15 исходных тестов проходят. Но `novelty=[]`, `critical_claims=[{}]` могут вызвать TypeError; вход не-dict также не обработан контрактом. До membership проверять типы, на API выдавать контролируемую ошибку/статус. Согласовать строгий профиль 90 дней и порядок branches/countersearch. Исходник передан без выдачи его за исправленный.
2. **Radar validator:** errors=[] возможно при пустом ledger и PASS без evidence. Он структурный; нужен отдельный semantic gate critical claims/evidence refs/edge endpoints. Не ломать легитимную валидацию пустого шаблона, отделить publish profile от template profile.
3. **POL:** пустой evidence JSONL может завершать helper кодом 0; return code не является разрешением публикации. Simulation deadline shortcut может опережать hard fail. Переносить приоритеты критических опровержений из предметного плана. Свежий аудит описывает и другие известные ограничения; не считать название версии доказательством их исправления на ВМ.
4. **GoalOps:** методология и YAML-примеры, не готовый scheduler или полный исполняемый валидатор. Не поднимать второй управляющий цикл поверх существующего GOAL.
5. **Auto-Goal:** аудит относится к commit 4e3257d8 от 17.09. Текущий main может отличаться; 14 старых проб не являются текущим regression result сервера. Брать контракты/приёмку из baseline, не устанавливать старый daemon.
6. **Eval/обучение:** frozen LLM и предметная логика остаются основой. ML-training requirement не закрывается промптом или названием `ts eval`; требуется согласованный target, набор с отрицательными/пограничными случаями, отсутствие утечки, метрики и воспроизводимый запуск. Убрать LogisticRegression можно, но нужно решить, что закрывает требование вместо него.

Минимальные product-сценарии: неизвестные/неверные типы; пустые critical claims; поддельные evidence refs; будущая дата; неполное окно; смена запроса; один независимый singleton; перепечатки одного события; зрелая родительская тема; критическое опровержение при deadline; полезное отрицательное evidence; повтор job/отмена/восстановление; чтение всех противоречий verifier. Проверки исходных доноров не заменяют эти сценарии backend.

Уже выполнено при сборке: выбор версий по manifests, безопасная распаковка, повторный запуск 15 policy tests, проверка файловых SHA256 при упаковке. Копии XLSX сверены по хешам. Установка, исправление helpers и приёмка продукта не выполнены.
